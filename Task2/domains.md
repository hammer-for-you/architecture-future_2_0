# Разделение на домены



### Принципы разделения на домены

Разделение на домены основано на следующих принципах:

- Bounded Context. Термины и понятия внутри домена должны иметь чёткое значение.

- Организационная структура компании. Тут следует учитывать закон Конвея. Также  разделение по границам подразделений компании представляется довольно естественным, поскольку, как правило, внутри подразделения используется один и  тот же bounded context.

- Изоляция данных. Каждый домен должен полностью владеть своими данными. То есть домен должен быть способен управлять ими, следить за качеством, следить за жизненным циклом и предоставлять данные как продукт.
  
  

Таким образом, у нас естественным образом получаются следующие домены:

- Медицинский - всё для работы клиник

- Финтех - оказание финтех-услуг

- ИИ-домен - обработка медицинских данных с помощью ИИ

- Корпоративный - обсепечение работы головного офиса



Соответственно, будущие партнёры тоже выделяются в отдельные домены. То есть в настоящее время, исходя из планов развития, можно предположить, что в системе появятся следующие домены:

- Электроника - производство медицинского оборудования

- Фармацевтика - фармацевтическое направление деятельности компании



### Аргументация в пользу разделения на домены

Разделение на домены позволяет оптимизировать бизнес-процессы и снизить издержки компании. Можно перечислить следующие преимущества:

- Эффективное использование данных, как следствие - снижение издержек. Разделённые по доменам данные имеют владельцев и документацию. Доверие к данным значительно выше.

- Снижение time-to-market новых фич/исправления багов. Разделение на домены позволяет вносить изменения в домен и выводить эти изменения на рынок, не опасаясь нарушить работу других доменов. Следовательно, новые фичи будут попадать в production быстрее.

- Повышение качества системы и снижение издержек на тестирование. Доменная изоляция позволяет при изменениях не тестировать всю систему целиком, а сосредоточиться только на домене, подвергшемся изменениям.

- Снижение издержек на открытие новых направлений. Также уменьшается время вывода нового направления на рынок. Разделение на домены позволяет разрабатывать новое направление обособленно, не отвлекаясь на на встраивание его в legacy DWH. Данные работы не затрагивают другие направления, следовательно требуют меньше ресурсов.

- Снижение издержек на масштабирование. Разделение на домены позволяет более гибко масштабировать сервисы. Теперь нет необходимости масштабировать всю систему целиком, можно маштабировать только проблемный домен. Как следствие - затраты компании при таком подходе снижаются.



### Потоки данных между доменами

Как следует из схемы С4, предполагается, что в целевой системе обмен данными между доменами будет идти через шину данных. Все изменения в данных сервисы публикуют в шину, а сервисы-потребители данных получают те события, на которые они подписаны и извелкают из них нужные им данные.

Отсюда следуют типовые сценарии, по которым происходит обмен данными. Благодаря event-driven архитектуре эти сценарии одинаковы для всех доменов, в том числе и будущих. Поэтому для краткости я приведу диаграммы потоков данных между двумя доменами - медицинским и доменом ИИ-сервисом. Потоки данных между другими доменами выглядят аналогично.

1. Обмен данными через шину. Это базовый сценарий обмена данными между доменами. Домен публикует свои данные в шине, домены-потребители получают данные, на которые они подписаны. [Диаграмма потоков данных](./pub-sub.drawio.xml).

2. Запрос данных их Data Lakehouse. Этот сценарий применяется в том случае, если  домену требуются данные, на которые он ранее не был подписан. Такое возможно, например, в случае внедрении нового функционала. В этом случае домен сначала обращается к Data Mesh, чтобы получить необходимый ему Data Product и понять, какие данные и как ему надо запросить. Далее домен запрашивает нужные ему данные в Data Lakehouse. [Диаграмма потоков данных](./query.drawio.xml).

3. Подключение к системе нового домена. Название данного сценария говорит само за себя. В этом случае новый домен обращается к Data Mesh, чтобы получить необходимые ему Data Product'ы. Далее домен публикует в Data Mesh свой Data Product, чтобы его могли использовать все заинтересованные домены. Следующим шагом домен подключается к шине данных, и дальнейший обмен данными идёт по ранее описанным сценариям 1 и 2. [Диаграмма потоков данных](./new-domain.drawio.xml).
